# AeroPulse System Architecture & Technical Specifications

## 1. End-to-End System Pipeline

```
[Physical ESP32 Weather Station]
  ├── BME280 (I2C: 0x76) ➔ Temp, Humidity, Pressure
  ├── Cup Anemometer (GPIO 14) ➔ Interrupt Frequency
  ├── Tipping-Bucket (GPIO 27) ➔ Reed Tip Interrupts
  └── SSD1306 OLED (I2C: 0x3C) ➔ Local Display
                 │
                 ▼  MQTT QoS 1 / TLS
       [Mosquitto MQTT Broker]
                 │
                 ▼  Topic: microclimate/v1/devices/{device_id}/telemetry
      [Backend Ingestion Service]
         ├── Schema Validation (Contract v1)
         ├── Device Auth & Topic ACL Matching
         ├── Sequence & Boot Session Tracking
         ├── Linear Sensor Calibration (val = raw * factor + offset)
         └── Data Quality Assessment (VALID, SUSPECT, INVALID, MISSING, STALE)
                 │
      ┌──────────┴─────────────────────────┐
      ▼                                    ▼
[PostgreSQL / TimescaleDB]       [Event Detection Engine]
  • telemetry_messages              • Configurable Multi-Rule Engine
  • measurements                    • Thresholds, Persistence, Cooldown
  • stations & devices              • Recovery Rules & Deduplication
  • incidents & evidence                   │
                                           ▼
                                 [Notification Dispatcher]
                                    ├── In-App Live Alerts
                                    ├── Email SMTP (Idempotent)
                                    └── Telegram Bot API
                                           │
                                           ▼  WebSocket Push (/ws/telemetry)
                              [React 18 TypeScript Frontend]
                                 ├── Command Overview & Live Meters
                                 ├── Diurnal Analytics & Historical Charts
                                 └── Station & Device Credential Management
```

## 2. Telemetry Contract v1 Schema

- **Schema Version**: `1`
- **Fields**:
  - `message_id`: Unique string ID generated by node per packet (prevents duplicate counting).
  - `device_id`: Registered hardware node identifier.
  - `boot_id`: UUID generated on ESP32 bootup to detect resets and reboots.
  - `sequence`: Monotonically increasing sequence number.
  - `timestamp`: ISO 8601 UTC timestamp synchronized via SNTP.
  - `uptime_seconds`: Node uptime in seconds.
  - `measurements`: Physical parameters (`temperature_c`, `humidity_pct`, `pressure_hpa`, `wind_speed_mps`, `wind_gust_mps`, `rainfall_interval_mm`, `rainfall_total_mm`, `rain_rate_mmh`).
  - `health`: Diagnostic telemetry (`battery_voltage_v`, `battery_percent`, `wifi_rssi_dbm`).

## 3. Data Quality & Sensor Health State Machine

Every incoming observation is evaluated and tagged with quality flags:

1. **VALID**: Value falls within physical terrestrial limits and passes rate-of-change checks.
2. **SUSPECT**: Rapid impossible jump (e.g. > 10°C change in one 10s interval) or frozen pattern.
3. **INVALID**: Sensor returns `NaN`, out-of-bounds voltage, or communication bus failure.
4. **MISSING**: Expected field null or sensor disabled.
5. **STALE**: Data age exceeds `DEVICE_STALE_THRESHOLD_SECONDS` (120s).

---

## 4. Event Detection Engine Mechanics

- **Threshold Rules**: High temperature, heavy rain depth, intense rain rate, high wind gust, rapid barometric drop.
- **Hysteresis & Recovery**: A distinct recovery threshold prevents alerting flapping when values oscillate near the trigger boundary.
- **Cooldown**: Prevents alert notification floods by enforcing configurable cooldown intervals.
- **Forensic Evidence**: Every incident retains an audit trail of triggering values in `IncidentEvidence`.
- **Deduplication**: In-app, Email, and Telegram notifications use deterministic idempotency keys (`{channel}-{incident_id}-{timestamp_bucket}`).
